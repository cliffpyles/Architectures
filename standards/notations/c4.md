# C4 notation

Rules for C4 model diagrams, in addition to the [diagram rules](../diagrams.md). Source: the C4 model by Simon Brown, <https://c4model.com>.

The C4 model sets the abstractions and levels. It does not prescribe shapes or colours. The shapes and colours below are this repository's fixed choices.

## Diagram types

| Type | Shows | Does not show |
|---|---|---|
| System context | The system as one element, its persons, the external systems it depends on | Containers, technology choices |
| Container | The containers inside one system boundary, the persons and external systems connected to them | Components, more than one in-scope system |
| Component | The components inside one container boundary, and the containers and external systems connected to them | Classes, more than one container's internals |
| Dynamic | The elements of one scenario, with numbered relationships in call order | Relationships outside the scenario |
| Deployment | Deployment nodes, nested, with the container instances that run in them | Components |

The code level is not drawn.

A container is a separately deployable or runnable unit: an application, a database, a file store, a queue. It is not a Docker container.

## Elements

| Element type | Shape | Palette row |
|---|---|---|
| Person | Circle (head) above a rounded rectangle (body). The label is inside the body. | Person |
| Software system (in scope) | Rectangle | In-scope software |
| Software system (external) | Rectangle | External system |
| Container: application or service | Rectangle | In-scope software |
| Container: database | Vertical cylinder | Data store |
| Container: object storage | Bucket (elliptical rim, sides tapering to a narrower base) | Data store |
| Container: queue, topic or stream | Horizontal cylinder | Data store |
| Container: CDN or other network edge | Cloud | Network edge |
| Component | Rectangle | In-scope software |
| System or container boundary | Dashed rectangle, no fill | Boundary |
| Deployment node | Solid rectangle, no fill, stroke width 1 | Boundary |

A container diagram distinguishes containers from external systems by palette row. A component diagram distinguishes components from the containers around them by the boundary: components are inside it, containers are outside it.

## Labels

Labels do not use square brackets. The shape, the palette row and the legend state an element's type.

Element label, centred:

```
<Name>                          size 20
```

- The label is the name only. The name and the element's relationships state its responsibility; the module README describes it where they do not.
- The name is at most two lines of 16 characters. Break lines explicitly.
- When a requirement fixes the technology, add it as a last line, size 16. Otherwise omit it.

Boundary label, at the top left inside the boundary, size 16: `<Name>`.

Deployment node label, at the top left inside the node, size 16: `<Name>`.

Relationship label:

```
<verb phrase>     size 16
```

- When a requirement fixes the protocol, add `via <Protocol>` as a last line. Otherwise omit it.
- On dynamic diagrams, prefix the verb phrase with the step number: `1. submits article`.

## Title

`<System name>`, with `: <subject>` appended for component and dynamic diagrams. The title does not name the diagram type; the module README does.

Examples: `Content Platform`, `Content Platform: CMS`, `Content Platform: publish an article`.

## Sizes

| Element | Width × height |
|---|---|
| Rectangle (system, container, component) | 200 × 80 |
| Person body | 200 × 70, with a head 44 in diameter |
| Cylinder, bucket | 200 × 110 |
| Horizontal cylinder | 200 × 80 |
| Cloud | 200 × 110 |

## Legend entries

Use these names: `Person`, `Software system`, `External software system`, `Container`, `Database`, `Object storage`, `Queue`, `Network edge`, `Component`, `Boundary`, `Deployment node`, `Synchronous request`, `Asynchronous event`, `Note`.
